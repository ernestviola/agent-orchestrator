## Project Direction — self-hosting

Committed goal: **run the orchestrator against this repo (`projectPath` = `/workspace`) to build its own features**, with the reviewer runtime intended as the first feature the orchestrator builds on itself. This reframes several "Open Questions" below from maybe-someday to prerequisites, and fixes an ordering:

1. Orchestrator loop + human approval gate — the entrypoint. Build by hand. **Done** (`src/orchestrator.ts`, `src/llm.ts`, `--orchestrate` CLI).
2. **Sandbox dependency support** — **Done.** `orq-project.json` gained `sandboxReadonlyPaths` (bind-mounted `:ro` from the real target — config, deps that are only read) and `sandboxWritablePaths` (`cp -a`'d into the working copy, mounted `:rw` — `node_modules`, because Vite/Vitest bundle the config into `node_modules/.vite-temp`). Both validated against `..` / credential-file patterns (`assertSafeSandboxPath`). Root `orq-project.json` added so `--orchestrate .` targets this repo. Cost ≈ one `cp -a node_modules` (~2s here).
3. Typecheck gate — **not yet.** Root `testCmd` is `npm test` only; strict `tsc` isn't run inside the sub-agent, so a sub-agent could introduce a type error `npm test` misses (vitest transpiles, doesn't type-check). Fold `tsc -p tsconfig.json --noEmit && npm test` into `testCmd` (or a `checkCmd`) as a follow-up — needs `tsconfig.json` in `sandboxReadonlyPaths` (already there).
4. Boundary handling — `src/roles.ts`, `.devcontainer/`, `tests/`, CI are AGENTS.md-protected. Engineer now reads `tests/` **read-only** (needed to verify its own work — see Decisions), still cannot modify a test. For the rest the protection is the approval gate: sub-agent edits a working copy, the diff goes to the human, the human rejects a sketchy `roles.ts` change before the orchestrator commits. A path denylist in working-copy staging is still optional defense in depth (not built).

## Decisions Made

- Orchestrator runs in a lightweight, non-hardened devcontainer (root user, Docker socket mounted, no egress proxy) — this is the trusted tier. Full harness hardening (capability-drop, non-root, egress allowlist) is reserved for the sub-agent containers this code provisions, not applied to this repo's own dev environment. See design doc's "Two-tier container security model."
- `node_modules` is deliberately NOT a Docker volume (named or anonymous) — it lives in the container's own writable layer only, to avoid volume bloat across many future projects. Consequence: a full `docker compose down`/`up` wipes it; `postCreateCommand` runs `npm install` automatically to restore it every time.
- Git identity/push access is set up in this container (identity via mounted `~/.gitconfig` include, auth via `GITHUB_TOKEN` PAT + credential helper baked into the Dockerfile). Sub-agent containers must never get this — see design doc's git-credential boundary section.
- Quality gate (pre-commit hook) is currently warn-only on all branches, including `main` — the branch-protected hard-block was deliberately removed for this first project's early-stage convenience. Flagged as temporary; revisit before this project has real stakes or other contributors.
- Bot identity for git (separate GitHub account for orchestrator commits) considered and deferred — not worth the setup cost yet for a single-user tool. Revisit if commit volume or attribution clarity becomes an issue.
- Credential naming convention: `.env.local`, provider-prefixed uppercase (`GITHUB_TOKEN`, `OPENROUTER_API_KEY`, etc.)
- Sub-agent container assets live in `sandbox/`, ported from `ai-dev-template`. **Follow-up:** once stable, lift `sandbox/Dockerfile` + the proxy assets back into `ai-dev-template` as a published GHCR base image consumed here by pinned digest; this repo's sub-agent Dockerfile then becomes a thin `FROM`. `sandbox/` is the extraction spec.
- Result handoff is an explicit interface (`ResultStore` in `src/types.ts`), not an implicit shared mount — `LocalResultStore` stages a per-run **working copy** (`.orchestrator-runs/<id>/work/{src,tests}`) that the sub-agent edits, and `finalize` returns a `git diff --no-index` of `work/{src,tests}` vs the real target (both dirs are diffed and concatenated; only the role's writable subtree can actually differ). The real target is never mounted writable. Chosen over chmod-in-place because (a) it is the stage-inputs / collect-outputs seam a **cloud** backend replaces with a volume / object store — chmod-in-place bakes in the shared-filesystem assumption; (b) it sidesteps root-owned-files vs `agent` uid 1000; (c) the diff is what the human approval gate will consume. Costs one `cp -r` per run (trivial for real src/+tests/).
- Target project is described by an `orq-project.json` manifest at its root, so nothing hardcodes layout or test command. Required: `testCmd`, `srcDir`, `testsDir`. Optional: `sandboxReadonlyPaths` (bind-mounted `:ro` from the real target at the same relative path under `/workspace` — config files, deps that are only read) and `sandboxWritablePaths` (`cp -a`'d into the per-run working copy and mounted `:rw` — for `node_modules`, since Vite/Vitest bundle the config file into `node_modules/.vite-temp` and a `:ro` mount there is EROFS). Both are validated by `assertSafeSandboxPath` (no `..`/absolute, no `.env`/`*.pem`/`*.key`/`*secret*`/`*token*`/`*credential*`/`.git`); a path can be in one list or the other, not both. `SpinUpParams.projectPath` selects the target (defaults to the orchestrator's own `/workspace`); `resolveTargetHostPath` maps an in-repo target to its host-daemon path for the `:ro` binds.
- Engineer role mounts `tests/` **read-only** (was: not mounted at all). Needed because the engineer runs `testCmd` to verify its work — with no `tests/` present, `node --test` finds zero files and exits 0, so every engineer run reported a vacuous "pass" on iteration 1 and never actually checked anything (the fizzbuzz e2e passed by luck). `docs/DESIGN.md` → Roles sanctions read-only ("mounted read-only if the task genuinely needs to read (not modify)"). Structural integrity is preserved — `:ro` makes modifying a test impossible; the `assertProfileInvariants` check just moved from "engineer has no `tests/` mount" to "engineer has no *read-write* `tests/` mount".
- In-container agent runtime = a minimal custom Node loop (`sandbox/agent/agent.mjs`), baked into `orq-sandbox:dev`, dispatching on `task.role`. Node builtins + `undici` only (Node 22's global `fetch` ignores `HTTP(S)_PROXY`; `undici`'s `EnvHttpProxyAgent` routes through the egress proxy). The model returns whole-file replacements for its role's one writable dir (`src/` for engineer, `tests/` for test-engineer — a bad path is also rejected in-code, but the mount mode is the real boundary). No shell access for the model. Two loop shapes: engineer = apply → run tests → feed failures back for up to `ORQ_MAX_ITERS` turns, success = tests pass; test-engineer = author test files once (retry only an unusable reply), then finish `completed` — its drafted tests are *expected* to fail against an unimplemented `src/`, so the human approval gate (not a green run) judges them; the test command is still run once and its outcome recorded in `status.json` (`testsPass`, `testExit`, `filesWritten`). Same loop shape the orchestrator will reuse.
- Model routing (`src/models.ts`) via OpenRouter (OpenAI-compatible). One model for all roles for now; per-task cost tiers deferred per DESIGN.md. Default `ORQ_MODEL=anthropic/claude-haiku-4.5`, overridable via env or `SpinUpParams.model` (was `anthropic/claude-3.5-haiku` until OpenRouter dropped that slug from its catalog — 404 "No endpoints found"). The orchestrator LLM has its own route (`selectOrchestratorModel()` / `ORQ_ORCHESTRATOR_MODEL`, same haiku default) — DESIGN.md wants a stronger model here eventually, but haiku does the tool-calling fine for now.
- Orchestrator loop (`src/orchestrator.ts`) = an LLM tool-use loop over ONE tool, `spin_up_agent(role, task, context?)`. It runs in the trusted tier with direct egress, so it uses a plain-`fetch` OpenAI-compatible client (`src/llm.ts`), not the sub-agent's proxy-aware one. `OrchestratorSession` holds the message history + gate state; `send(userInput)` drives the model through any tool calls (capped at `MAX_TOOL_ROUNDS` per turn) to a text reply. The **human approval gate is enforced in the tool handler, not the prompt**: `dispatchTool` refuses `role: 'engineer'` while `testEngineerRuns > 0 && !testsApproved`, and after every *completed* test-engineer run it calls the injected `approveTests(result)` (a deterministic CLI y/n on the diff) and records the verdict. No prior test-engineer run ⇒ engineer is allowed (implementing against pre-existing human tests). `reviewer` is refused (runtime not built). `--orchestrate [projectPath]` in `src/index.ts` wires a `node:readline/promises` REPL to it; EOF/Ctrl-D during the gate ⇒ NOT approved. The orchestrator does no git — the human commits.
- Egress proxy is **per run** (one tinyproxy container + one internal network per sub-agent), not a shared long-lived proxy — matches "disposable per task" and makes per-role allowlists trivial later. Revisit if per-run startup latency matters.
- `.orchestrator-runs/` (per-run in/out scratch) is ignored via `.git/info/exclude` (local, uncommitted) to avoid touching the `.gitignore` boundary file.

## Open Questions

- Whether model selection (per-task, cost-driven) lives in the orchestrator's own reasoning or in deterministic provisioning-layer code — noted as undecided in the design doc.
- Exact GitHub PAT scope for eventual "orchestrator creates its own repos" capability — deferred; current token is scoped to this repo only, without repo-creation permission, until that capability is actually being built.
- Sub-agent root filesystem stays `--read-only` (tmpfs for `/tmp`, `~/.cache`). Deps for a real target now come via `sandboxReadonlyPaths` / `sandboxWritablePaths` (a `cp -a` copy for anything the test runner writes into), not a writable rootfs or an in-sandbox `npm ci`. The sandbox image still has **no `git`** on purpose (the "sub-agents never do git" line) — so the 4 `LocalResultStore.finalize` unit tests that shell out to `git diff --no-index` are `it.skipIf(!HAS_GIT)`; they run in the orchestrator/CI and skip when the suite runs inside a sub-agent.
- Engineer's uid-1000 write problem is **solved for now** by the working copy (`chmod -R a+rwX work/src` on a throwaway dir). A cloud backend or a huge repo will want something better (worktree / overlayfs / run-as-host-uid).
- `OPENROUTER_API_KEY` is injected into proxy-network sub-agent containers as a *model* credential — explicitly NOT the git-credential boundary. `spinUpAgent` throws early if it is unset; kept out of logs. Must be in `.env.local`.
- The real-model leg (`undici` → egress proxy → OpenRouter) is exercised only by the `it.skipIf(!OPENROUTER_API_KEY)` integration tests (one per role). `agent.mjs` itself has no unit test yet — a CONTEXT note previously claimed a stub-server test exists; it does not. Worth adding.
- Only **in-repo** target paths are wired (`resolveTargetHostPath` throws for a path outside the orchestrator's `/workspace`). Pointing `--orchestrate` at `/workspace` itself (self-hosting) now works end to end. Arbitrary out-of-repo target repos are still future.
- `resolveTargetHostPath` assumes the orchestrator process runs with its cwd under `/workspace` (true via the npm scripts). A follow-up could derive the target subpath more robustly.
